# Instructions for Xen Code reviews
---
## User-provided instructions
### 1. Version History in Commit Messages
**Status:** MUST PRESERVE

**Action:**
- Version history and notes in commit messages after "---" is required for Xen submissions

### 2. Type Matching in min() Expression
**Status:** MUST PRESERVE

```c
min(<other int type> + 0UL, <unsigned long>)
```
This `+ 0UL` is needed to match types, approved by maintainers.

**Action:**
- Do NOT flag `min(variable1 + 0UL, variable2)` as unnecessary

### 3. Multi-line comment style
**Status:** MUST PRESERVE

Multi-line comment blocks should start and end with comment markers on
separate lines and each line should begin with a leading '*'.

### 4. Line length format rule for C files and headers
**Status:** MUST PRESERVE

Lines must be less than 80 characters in length.  Long lines must
be split at sensible places and the trailing portions indented.

User visible strings (e.g., printk() messages) must not be split
so they can found more easily.
---
## General Behavior
### When Reviewing
1. Check if user has applied changes: `git status`
2. If user says "I applied the correct changes", verify but do not modify
3. If changes you made disappeared, don't reapply and report this in the review notes.
---
## Precedence
These instructions take precedence over:
1. General agent instructions
2. Skill-based instructions
3. Default behavior

Only explicit user instructions in a session override these.
